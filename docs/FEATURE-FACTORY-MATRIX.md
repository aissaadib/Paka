## 0. Method, ID namespaces and what this document is not

### 0.1 Method

1. **The clone inventory was verified, not assumed.** Every licence below was read
   from the clone's own licence file in this session, and the identifier line is
   quoted verbatim. The two sparse-checkout clones were read from the **git
   object database** (`git ls-tree`, `git show HEAD:<path>`), never by changing
   the sparse filter.
2. **Paka's baseline was established from the code**, not from the UI and not
   from prose. `AGENTS.md` in the Paka repo was the reading protocol: grep for a
   symbol, read a ±40-line window, read tests by name, never read a file over
   250 lines end to end. The only files read whole were `src/types/brush.ts`
   (98 lines), `src/core/tools/shapeGeometry.ts` (182 lines) and
   `src/utils/color.ts` (55 lines).
3. **A feature Paka implements differently is not a gap.** Only *missing
   capability* is recorded as a gap; a *different implementation* is recorded as
   "not a gap" and is explicitly excluded from the count of real gaps.
4. **Provenance is decided per capability, not per repository.** A repository can
   be `COPY-ELIGIBLE` for one row and `REFERENCE-ONLY` for another, because the
   licence attaches to the file, not to the project.
5. **No upstream artefact was read for this document that I did not open.** Where
   a source file is named below, I opened it or listed it with `git ls-tree` in
   this session.

### 0.2 ID namespaces (the convention this document establishes)

The repository currently overloads `T-nn` for **two different things**. This
document introduces three distinct namespaces and uses them consistently.
**No historical artefact is renamed.** The mapping to the existing labels is:

| Namespace | Prefix | Meaning | Existing label it maps to | Where the existing label lives |
| --- | --- | --- | --- | --- |
| **feature** | `FF-nn` | A creative capability Paka lacks (or has only partially). **New rows in this document use this prefix.** | *(none — new)* | `wave0/FEATURE-MATRIX.md` §4 |
| **analyst-test** | `AT-nn` | A historical analyst *test* row: an observable behaviour with a setup and an expected result. | `T-01` … `T-32` | `docs/acceptance-criteria.json` → `criteria[].analystTestIds`; `docs/g1/feature-evidence.json` → `tests[]`. **31 distinct ids are in use; `T-22` is not referenced.** |
| **task** | `TASK-nn` | A feature-factory **implementation task** (a unit of work with a branch, a file scope and an exit condition). | `T-00a` … `T-58` | `Paka-feature-factory/audit/12-roadmap.md`; `STATE.md`; `wave1/`; `worktrees/` |

Rules that follow from this:

- A `TASK-nn` reference in this document **always** names the factory task, and
  I write the historical label in parentheses on first use, e.g.
  "TASK-10 (historical `T-10`)".
- An `AT-nn` reference **always** names an analyst test row, and I write the
  historical label in parentheses on first use, e.g. "AT-05 (historical `T-05`)".
- A `FF-nn` reference **always** names a row of §4.
- The three namespaces never overlap. `T-10` in the roadmap (a task) and `T-10`
  in `docs/acceptance-criteria.json` (an analyst test) are **different things**;
  this document refuses to perpetuate that ambiguity.

### 0.3 What this document is not

- It is **not** a licence clearance. `COPY-ELIGIBLE` means *permissive enough
  that copying is legally possible*, not *approved*. The factory's Licence Gate
  (`Paka-feature-factory/AGENTS.md` rule 2) is still a hard stop before any
  source-derived implementation begins.
- It is **not** a plan of record. `docs/ROADMAP.md` "Next slice" remains the
  authority on what Paka builds next; this document is the *capability* view.
- It is **not** a re-statement of the 77-gap matrix in `audit/11-gap-matrix.md`.
  That document is a per-repository gap list; this one is deduplicated,
  provenance-graded and prioritised.
- It is **not** a commitment to reproduce Photoshop, Krita or Adobe Animate.
  Ranked by *meaningful creative capability per unit of complexity and risk*.

### 3.3 The rules that decide what fits

Quoted from the live docs, because they decide every "Proposed" cell below.

- *"The document model is authoritative; pixel buffers are rebuildable caches."* — `docs/SESSION-BRIEF.md` §1.
- *"Strokes are self-describing: `brush`, `erase?`, `fill?`, sample arrays … Re-rasterizing never consults tool state."* — §6.
- *"Opacity is applied once per stroke … Never lower per-segment alpha to fake softness."* — §6.
- *"Live / commit / undo-redo rebuild / reopen / PNG export must produce the same pixels at any zoom and `rasterScale`."* — §6, §9.
- *"Determinism: no `Math.random()`, no time, no zoom dependence in a repaint path."* — §6, §9.
- *"The React layer has no automated tests; pure logic must be extracted into DOM-free modules to be testable."* — §5 rule 6.
- *"Editor options are session state: not an edit, no history, no dirty flag."* — §6.
- *"A new rendering strategy is a rasterization strategy, **not** a new element kind — a genuinely new element kind needs a format bump and an older reader must refuse the file rather than draw a different picture."* — §6, and `docs/ROADMAP.md` "Next slice".
- *"Document raster budget: 16,777,216 px, 58 bytes per document pixel."* — §6; `src/core/document/document.ts:128` (`estimateDocumentRasterBytes`).

| 7 | **FF-02** stroke taper and pressure easing | The largest single jump in brush *feel* per unit of work. `perfect-freehand`'s easing maths is **MIT** and pure; Paka's brush already has `pressureSize` and `minSizeRatio`, so the vocabulary exists. | 8 | **FF-25** more layer blend modes | The cheapest format-aware feature on the matrix (**S**). `normal`/`multiply`/`screen` are the only three today; Canvas 2D already implements `overlay`, `soft-light`, `colour-dodge`, `hard-light` and `difference` — **no new render path**, no new surface, no new rasterisation strategy. It reuses the existing composite path that display, export and bucket sampling already share. |
| 9 | **FF-46** native file dialogs + reveal in folder | **S** complexity, a plugin that can be adopted directly, and a **daily-use** gap: today the user cannot browse to a folder. A plugin adoption is the cheapest kind of work in this factory. |
| 10 | **FF-27** alignment guides + grid + snapping | High perceived polish for **M**. `fabric.js`'s `aligning-guidelines` maths is **MIT** and **pure** (points in, candidate alignments out) — directly reusable. The one thing to *not* copy is Fabric's screen-space margin, which would break Paka's zoom-independence rule. |

**Honourable mentions, and why they are not in the top ten.**
- **FF-04** image/pattern brush tip — arguably as valuable as FF-02, but it is a
  superset of FF-08 and needs an asset policy for the tip images.
- **FF-20 / FF-21** layer groups and masks — the highest creative value on the
  matrix, but both need a **format bump** *and* a re-derivation of the 58
  bytes/document-pixel raster budget, which makes them **L** with a real risk of
  a budget regression.
- **FF-32** vector paths / pen tool — the highest ceiling (**XL**), but the
  flattening-density invariant (D-3) is the single most dangerous invariant in
  Paka, and it must be right the first time.
- **FF-35** SVG import — high value at **M**, but it is downstream of FF-32's
  flattening work.

## 9. Recommended implementation queue

The queue respects the factory's hard rules: **one writer at a time**, **one
feature per slice**, **one format bump at a time** (the bumps are serialised so
that only one version bump is in flight), and the Paka rule that a new element
kind requires a bump whose older reader **refuses** the file.

### Wave A — no format bump, no renderer change, no engine invariant touched

These rows produce **no** new element kind, no new blend-mode value and no
appearance-changing document field, so they need no version bump and can be
parallelised across writers as long as they do not share files.

## 10. Limitations

1. **The licence classes are legal-risk assessments, not legal advice.** The
   factory's Licence Gate remains a hard stop before any source-derived
   implementation. `COPY-ELIGIBLE` means *permissive enough that copying is
   legally possible*, not *approved*.
2. **The `chroma.js` closure condition is the most likely place to get it
   wrong.** The package is `(BSD-3-Clause AND Apache-2.0)` and the two parts
   live in the same directory tree. Any adaptation must exclude `src/colors/**`
   and record the BSD-3-Clause notice. A reviewer who treats the whole package
   as BSD will ship colourbrewer data under the wrong licence.
3. **`fabric.js` is MIT, but "MIT" does not mean "copy it into Paka".** Most of
   its value is behaviour; its *scene-graph* model is incompatible with Paka's
   document model, and Paka's stack rule explicitly forbids a Fabric.js
   adoption or a renderer rewrite. Every row that names it is
   `REFERENCE-ONLY` except the three that name genuinely pure, portable maths
   (`aligning-guidelines` distance functions, `util/path` parsing, and the
   individual 2D filter kernels).
4. **The `e2e` goldens are Fabric's pixels and are useless to Paka.** The
   reusable asset is the *harness pattern*, not the images. Paka already has its
   own harness.
5. **The sparse clones were read from the git object database.** `fabric.js`'s
   worktree shows 2 of 10 packages and `tauri-apps-plugins-workspace`'s shows
   1 of 31. Anyone re-verifying by listing directories will get different
   answers; the tree listing is the truth. **No sparse filter was changed.**
6. **`perfect-freehand` is a poor fit for Paka's model.** It produces an
   *outline polygon*; Paka rasterizes a *coverage buffer* and unions per-pixel
   maxima. Only the point maths (easing, thinning, caps, simulated pressure) is
   reusable, and it must be re-expressed against Paka's dab/segment path.
7. **`opentype.js` solves the wrong half of the text problem.** It parses
   fonts and gives glyph outlines. It does **not** answer *which font* Paka
   should use on another machine — that is the owner's D-1 decision, and no
   amount of upstream code resolves it. The bundled test fonts include a
   **CC BY-SA** asset that must not ship.
8. **Paka's own baseline is moving.** The main checkout is at `108046f` on
   `feat/stamp-brush-engine`; FF-10's implementation (`dbcb446`, merged to
   `bc062c7`) lives in worktrees and is **not** in the main checkout. This
   document's baseline statements are about `108046f`.
9. **The §8 counters were tallied row by row and each total was checked to sum
   to 60.** An earlier draft's hand-written sub-counts disagreed with their own
   id lists; those tables were replaced with tallies that reconcile, and the
   ids are printed next to every count so the arithmetic can be re-checked
   without re-reading §4.
10. **The React layer remains untested**, so every "Acceptance" cell that
    involves a widget is a *manual* criterion with a DOM-free unit test
    alongside it (FF-58). No row in this matrix can be closed by an automated
    React test, because Paka has no React test framework and adding one is
    explicitly out of scope.
11. **Nothing was implemented and no test was run.** This document is analysis
    only. The Paka checkout was read, never written: `git status` shows the
    same paths as before this session.
12. **The prior 77-gap matrix (`audit/11-gap-matrix.md`) was not re-verified
    row by row.** I used it for orientation and cross-checked the load-bearing
    claims against the code, but the counts in the two documents are not
    reconcilable and I did not attempt to force them to be.
